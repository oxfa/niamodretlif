# Pipeline Artifact Handoff Implementation Plan

**Status:** The workflow and path layout implement the combined worker-input artifact, separate prepared-batch handoff, per-worker result uploads, and exact-ID result correlation. Worker manifests are required for every configured worker, including empty assignments; missing manifests fail rather than entering a nonparticipating branch. Worker status reads and lifecycle writes validate the requested batch and worker identity. Cache writes, persisted timestamps, and read cutoffs require timezone-aware values; aggregate cache merging skips invalid timestamp rows before selecting a winner; cache reads continue through matching rows until they find a valid fresh entry. Existing cache files require the expected user-visible table set and ordered column metadata, including declared types, nullability, defaults, hidden-column metadata, and composite identity-key ordinals; pre-existing empty, partial, and extended cache schemas are rejected before processing. Only an absent database path is initialized with the current schema. Artifact metadata requires a valid SHA256 digest, and downloaded worker-result archive bytes are checked against that digest. The latest focused local run passed 216 tests across cache schema/timestamp handling, artifact correlation, handoff, config validation, and filtered output; it covers strict marker checks, cache-shape rejection, mandatory digest checks, explicit-null rejection, late cache-read failure atomicity, rejection of pre-existing empty caches while preserving missing-path initialization, and unactionable registrable-domain TXT output. Earlier focused runs passed 127, 23, 73, 74, 75, 133, 166, and 172 tests. A production pipeline run remains outstanding. Receipt-step retrieval and reusable-workflow job names were observed in the controlled experiment below, but the raw timestamp prefix in an authenticated step-log response is still unverified.

## Objective and scope

For a normally completed run with N configured workers and successful uploads, create one combined worker-input artifact, one prepare-to-aggregator artifact, and N worker-to-aggregator artifacts: N+2 interstage artifacts total. Every runtime worker downloads the combined artifact and restores only its own named assignment directory. The logical handoffs remain prepare-to-workers (1→N), prepare-to-aggregator (1→1), and workers-to-aggregator (N→1). The final aggregate debug-log artifact remains an aggregate-stage output outside those interstage counts. The Actions cache is outside this artifact contract.

N means the configured worker count directly. Create one combined runtime-worker input artifact named `workflow-internal-combined-worker-inputs-<batch_id>`. It contains one directory for each configured worker, including workers with empty assignments. Do not create per-worker input artifacts or a duplicate legacy `workflow-internal-worker-manifests` artifact. The `prepare_run` job uploads the combined artifact and separate prepared-batch artifact; the `run_workers` matrix uploads the N worker results.

Both current reusable-workflow callers configure N=18. A successful run therefore creates 20 interstage artifacts: one combined worker input, one prepared-batch artifact, and 18 worker results. The current worker-count validator accepts 1 through 20; reject values outside that range before preparation with a clear error. The worker matrix creates at most 20 matrix-generated jobs at N=20, below GitHub's 256 matrix-generated jobs per workflow-run limit. The current 500-artifacts-per-job limit is also well above the two artifacts uploaded by `prepare_run`. See the [worker-count validation](../src/domain_pipeline/pipeline_run/settings.py), [Actions limits](https://docs.github.com/en/actions/reference/limits), and [matrix strategy](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstrategymatrix).

The existing `prepare_run` job creates all worker manifests and uploads the combined worker input plus prepared-batch artifact. Each `run_workers` matrix job downloads the combined input, restores only its worker directory, and creates its worker-result archive. The existing aggregator downloads the prepared-batch and selected worker results.

## Archive contract

### Combined worker input: one artifact

Create one artifact named `workflow-internal-combined-worker-inputs-<batch_id>`. Its successful-run contents include the exact worker-input members for every configured worker ID, including workers with empty assignments. Preserve each per-worker manifest at its canonical path:

```text
.workflow_state/batches/<batch_id>/workers/<worker_id>/runtime-config.json
.workflow_state/batches/<batch_id>/workers/<worker_id>/worker-identity.json
```

This archive is the prepare-to-workers handoff. Each runtime worker selects its own directory after downloading it; the archive is not included in the prepare-to-aggregator handoff.

### Prepare to workers: one artifact, N assignments

Each runtime worker downloads `workflow-internal-combined-worker-inputs-<batch_id>` and restores its own payload from `.tmp/combined-worker-inputs/<worker_id>`. Before copying the two JSON members to their canonical paths, restore checks the batch and worker IDs in both files and the configuration name in `runtime-config.json`. The worker opens only its own assignment and effective profiles. The runner has downloaded the full archive, so artifact names do not provide per-worker authorization. See the [Prepare to Worker JSON manifest contract](prepare-to-worker-json-manifest-design.md) for the payload and validation rules.

### Prepare to aggregator: one artifact

Create one artifact named `workflow-internal-prepared-batch-<batch_id>`. Its successful-run contents are:

```text
.workflow_state/batches/<batch_id>/output-config.yaml
.workflow_state/batches/<batch_id>/worker-ids.csv
.workflow_state/batches/<batch_id>/manual-domains.csv
.workflow_state/batches/<batch_id>/preparation-review.csv
.workflow_state/batches/<batch_id>/preparation-terminal.yaml
.workflow_state/batches/<batch_id>/source-formats.csv
.workflow_state/batches/<batch_id>/source-line-index.csv
.workflow_state/batches/<batch_id>/source_inputs/...
.workflow_state/batches/<batch_id>/source-items.jsonl
.workflow_state/batches/<batch_id>/source-item-index.json
.workflow_state/batches/<batch_id>/source-item-diagnostics.jsonl
.debug_artifacts/prepare/validation/logs/settings.yaml
.debug_artifacts/prepare/validation/logs/validate-settings.log
.debug_artifacts/prepare/batch/logs/batch.yaml
.debug_artifacts/prepare/batch/logs/prepare-batch.log
```

Do not copy the whole batch directory: its worker manifests belong to the combined worker-input artifact, not to the prepare-to-aggregator archive.

The source-input directory is optional only when the batch has no configured sources. All other runtime members, including the source-item records, index, and diagnostics file (which may be empty), are required after successful preparation. On a preparation failure, stage and upload any diagnostics already available using the same batch-scoped naming rule. Derive the batch ID before fallible preparation from the preparation job's run ID and attempt using the existing batch-ID rule, and use the same value for preparation and the upload name. The aggregator remains skipped because its current job condition requires successful preparation.

Batch-scoped prepare names distinguish preparation executions within one workflow run. Consumers use the `prepare_run` batch ID output, including when preparation is not rerun; they do not derive a name from their own current attempt. Require the expected batch ID and, for worker input, worker ID in the restored manifest. If the expected artifact or identity is missing or mismatched, stop that handoff without looking up another batch.

The validation and batch commands initially write `settings.json`, `validate-settings.log`, `batch.json`, and `prepare-batch.log` at the workspace root. The handoff layout archives the JSON payloads as `settings.yaml` and `batch.yaml`; diagnostic export converts those YAML members back to JSON for the final debug archive. The copies or staging must remain failure-aware so diagnostics produced before a failed command can still reach the prepared-batch archive.

### Workers to aggregator: N artifacts

Each configured worker matrix job stages and uploads one artifact named `workflow-internal-worker-bundle-<batch_id>-<worker_id>` when worker initialization reaches the handoff path. The batch ID comes from `prepare_run`, including on partial reruns. On normal worker completion it contains the result manifest, finalized status, and diagnostic logs at their canonical paths:

```text
.workflow_state/worker-results/<batch_id>/<worker_id>/handoff-state.yaml
.workflow_state/worker-results/<batch_id>/<worker_id>/unactionable-registrable-domains.txt
.workflow_state/worker-results/<batch_id>/<worker_id>/review-results-by-registrable-domain.csv
.workflow_state/worker-results/<batch_id>/<worker_id>/terminal.yaml
.workflow_state/worker-results/<batch_id>/<worker_id>/cache.sqlite3 (when a cache snapshot is present)
.workflow_state/status/<batch_id>/<worker_id>.yaml
.debug_artifacts/workers/<batch_id>/<worker_id>/logs/worker.log
.debug_artifacts/workers/<batch_id>/<worker_id>/logs/cache.log
```

For a successfully completed worker, the handoff state, status, unactionable-domain file, review CSV, and terminal rows are required. The cache snapshot is required when the handoff state declares one; worker and cache logs are optional diagnostics. For an initialized worker failure, include whichever manifest, status, result files, cache, and logs were actually produced. Do not manufacture a success-shaped file to fill a missing member. A failure before initialization completes does not upload a worker result artifact, even if earlier cache diagnostics exist; that worker is incomplete.

## Path-layout design

The current implementation already has `WorkflowStatePathLayout`, `PathLayout.workflow_state`, `PrepareToWorkerPathLayout`, `PrepareToAggregatorPathLayout`, and `WorkerToAggregatorPathLayout`. Keep those owners and correct their member lists to the persisted contract; do not add a parallel path API.

Each directional layout owns the exact member list for its logical handoff. For prepare-to-workers, the layout exposes a per-worker member list: prepare stages the exact union for all configured IDs into the combined worker-input archive, and each runtime worker restores only the list for its own `worker_id`. A member records its source path and archive-relative path; it does not carry an artifact name or upload settings.

The prepare-to-worker layout declares the two JSON files listed above.

The prepare-to-aggregate layout carries `output-config.yaml`, worker IDs, manual domains, prepare review/terminal rows, source formats, source-line index, source archives, diagnostics, source-item records/index/diagnostics; only the source-input directory may be absent when there are no sources. Current worker result paths use `worker-results/.../handoff-state.yaml` and status `.yaml`, not the former plan's `workers/.../worker-aggregate-manifest.json` and status `.json` names.

Compose the directional layouts with the shared workflow-state and output layouts. Do not inherit the broad workflow-state API into each directional layout. `OutputPathLayout` already owns the preparation validation/batch log and worker cache-log paths needed by the member lists.

Keep source paths and archive-relative paths explicit so staging and uploads do not reconstruct path strings independently in YAML, shell, and JavaScript. Use canonical `.workflow_state` and `.debug_artifacts` paths in the archives.

## Workflow changes

1. Keep batch preparation and creation of all N worker manifests in the existing `prepare_run` job.
2. Keep the existing Python staging and whole-set validation in `prepare_run`. Stage the combined worker-input directory from the exact union of per-worker member lists. Extend the existing handoff stager for the source-item records, index, and diagnostics.
3. After successful batch preparation, upload `workflow-internal-combined-worker-inputs-<batch_id>` once from `prepare_run` with `actions/upload-artifact@v7`, including hidden files. Require all expected worker manifests and use `if-no-files-found: error`; a failed combined upload fails preparation and prevents workers from starting. Do not use the removed local Node uploader or `@actions/artifact` package for per-worker uploads.
4. Stage preparation runtime members and all available preparation diagnostics into the separate prepared-batch directory, running the staging step with `if: always()`. Upload it once with `actions/upload-artifact@v7`, also using `if: always()` so available diagnostics remain if preparation or the combined-input upload fails. Include hidden files. The staging command requires runtime members when preparation succeeded; the upload uses `if-no-files-found: ignore` so a failed prepare can still retain any diagnostics that exist. A staging failure still fails preparation and blocks workers and aggregate.
5. Make `run_workers` depend directly on `prepare_run`. Each runtime worker downloads `workflow-internal-combined-worker-inputs-<batch_id>`, restores only its `worker_id` directory from that archive, and checks the manifest identity before use. The aggregator downloads only `workflow-internal-prepared-batch-<batch_id>` and validates the prepared source-item handoff identity. Keep worker IDs as a small job output; do not pass manifest bodies through job outputs. Remove `.github/artifact-uploader` and its Node dependencies after the hosted path is in place.
6. Retain the `run_workers` job name `Run workers` and its `worker_id` matrix, so each matrix job has the observed unambiguous name containing its worker ID. Set worker-matrix `fail-fast: false` so sibling workers can finish and retain diagnostics after another worker fails. Stage its worker-result members from `WorkerToAggregatorPathLayout` and upload that directory once as `workflow-internal-worker-bundle-<batch_id>-<worker_id>` in a uniquely named `Upload worker bundle` step using `actions/upload-artifact@v7`, with hidden files included and `if-no-files-found: error`. Give the step an ID. Immediately afterward, a uniquely named `Record worker artifact receipt` step prints exactly `ARTIFACT_RECEIPT <run_id> <batch_id> <worker_id> <artifact_id>`, using the numeric `artifact-id` output of that upload. The marker has no embedded format label. Require a positive decimal artifact ID at production and parsing, and require the receipt step number to equal the upload step number plus one. Run the receipt step when the upload succeeded even if an earlier worker step failed, using an explicit status condition; do not print a receipt when the upload failed or was skipped. The worker job is the sole producer of its batch-and-worker artifact name. Remove the separate worker debug upload; its log files are members of the result archive.
7. After workers finish successfully, the aggregator queries the current run's GitHub Actions jobs API with `filter=latest` and complete pagination. For the existing callers' `batch` job and the retained worker job name and matrix, match the exact API name `batch / Run workers (<worker_id>)` for each expected worker ID; require exactly one completed worker job and exactly one successful `Upload worker bundle` step and receipt step, with the receipt immediately following the upload. The exact names are supported by the controlled reusable-workflow observation below, not asserted as a universal GitHub naming guarantee. A failed worker job fails the matrix and prevents aggregate from starting; an artifact uploaded before that failure is diagnostic-only and is not selected by the aggregator in that failed run attempt. Fetch each successful receipt step's log using its selected job ID and API-reported step number, and parse exactly one receipt record with matching run, batch, and worker identities and a positive decimal artifact ID. GitHub's REST documentation specifies that this endpoint returns plain-text step logs, but the raw timestamp-prefix representation has not been verified here; do not assume or accept an arbitrary prefix. Use API version `2026-03-10` exercised by the experiment. Do not infer the producer from a latest job ID or attempt number: GitHub may list a new record for an untouched job on a partial rerun. Preserve the aggregator's existing `actions: read` permission and its callers' corresponding permission.
8. For each worker whose job and receipt passed the checks, retrieve artifact metadata by the recorded ID and require the expected batch-and-worker name, current workflow run ID, a nonexpired artifact, and a lowercase `sha256:` digest with 64 hexadecimal digits. Download that exact ID with GitHub's artifact REST download endpoint into a worker-specific staging location, validate the archive's allowed canonical paths and manifest/status identities before restoring its members, and always compare the downloaded archive bytes with the required digest. Missing, null, malformed, or mismatched digest metadata fails correlation before archive download or restore. A missing, ambiguous, or invalid result artifact fails correlation in the aggregate job before the readiness barrier or aggregate source-item/output processing; the aggregate job fails without publishing output. Because this retrieval runs inside aggregate, do not claim that it retroactively makes the worker matrix unsuccessful or the aggregate job skipped. Do not recover by substituting a stale bundle. Do not use `actions/download-artifact@v8`'s multi-ID selection as proof that every requested ID was retrieved: the controlled observation below shows a successful step that omitted one requested ID. Treat a missing or incomplete jobs listing as an incomplete correlation result rather than assuming unseen jobs do not exist.
9. Keep the existing final `debug-pipeline-run-log-<config_name>-<batch_id>` upload from the aggregate job. Update its staging to read preparation diagnostics and accepted worker logs from the new handoff locations while preserving the final archive's established diagnostic paths. Remove the standalone `debug-validation-settings` and `debug-prepared-batch` uploads and the separate worker debug uploads.

The workflow's `worker_ids_json` remains a small matrix input; manifest contents stay in files and artifacts. GitHub limits job outputs to 1 MB per job, and the prepared manifest's `delegation_roots` map is derived from assigned domains.

## Failure behavior

The logical handoffs remain N prepare-to-worker assignments, one prepare-to-aggregate handoff, and N worker-to-aggregate results. On a fully successful run, the physical interstage artifact count is N+2: one combined worker input, one prepared-batch artifact, and N worker-result artifacts. At N=18, that is 20 artifacts. The `prepare_run` job uploads the combined worker input and separate prepared-batch archive. If preparation or the combined-input upload fails, `prepare_run` fails, the worker matrix does not run, and aggregate is skipped; the prepared-batch archive may still preserve available diagnostics.

Keep worker-result upload after handoff/status finalization and run it with `always()` once initialization completes. A worker that fails after producing status or handoff data can still upload those files and available logs for diagnosis. Any unrecoverable worker failure fails the worker matrix; `fail-fast: false` lets sibling workers finish, so aggregate never starts in that failed run attempt. The aggregate does not retrieve that failure bundle, synthesize missing worker status, or run the readiness barrier. Remove the unreachable incomplete-status materializer step and its CLI/lifecycle route; exact-ID correlation already exits nonzero for incomplete worker results, so dependent readiness steps are skipped. Failure finalization remains responsible for writing a terminal status within the worker job and retaining any finalization error for its error annotation. After a successful worker matrix, the aggregate job performs exact-ID correlation and retrieval before the readiness barrier and aggregate processing. A correlation or retrieval failure fails aggregate before source-item processing or output publication; a fatal worker execution error instead fails the worker matrix and skips aggregate entirely.

### Controlled rerun observation

The isolated [observation workflow](https://github.com/oxfa/niamodretlif/blob/dbd588359a703727863651499b6bf7067d8fd6b9/.github/workflows/artifact-rerun-observation.yml) used two synthetic workers, `actions/upload-artifact@v7`, and `actions/download-artifact@v8` without a token input. It did not run the pipeline or its readiness code. The [workflow run](https://github.com/oxfa/niamodretlif/actions/runs/45050072240) used commit `dbd588359a703727863651499b6bf7067d8fd6b9`.

- Attempt 1 succeeded and created worker-01 artifact `14765042837` and worker-02 artifact `14764983272`, each with an attempt-1 marker.
- In [attempt 2](https://github.com/oxfa/niamodretlif/actions/runs/45050072240/attempts/2), worker-02 was rerun and failed before upload. The [observer](https://github.com/oxfa/niamodretlif/actions/runs/45050072240/job/137293282975) successfully downloaded both attempt-1 artifacts, including the old worker-02 marker. The untouched worker-01 artifact was also available.
- In the full rerun, worker-01 uploaded artifact `14765545158` with marker `worker-01 3`, while worker-02 failed before upload. The [observer](https://github.com/oxfa/niamodretlif/actions/runs/45050072240/job/137293628410) found only the new worker-01 artifact and extracted it directly into the download directory.

These results establish the behavior for this run and its tested actions and inputs. They do not prove behavior for every rerun or establish how the pipeline readiness barrier responds. The partial rerun demonstrates that a name-pattern download can return a stale successful worker handoff, so a missing-artifact check alone is insufficient.

Preparation has a separate rerun concern: the existing batch ID includes the preparation attempt, so rerunning preparation produces a different batch while the former plan's prepare artifact names stayed the same. The experiment demonstrated coexistence of same-named artifacts in reruns, and the [artifact toolkit's latest filter](https://github.com/actions/toolkit/blob/main/packages/artifact/src/internal/find/list-artifacts.ts) orders IDs numerically. The observed later worker upload's ID was lower than its earlier ID. Therefore that ordering does not establish the desired preparation execution; batch-scoped prepare artifact names and payload checks avoid relying on it. The controlled experiment did not execute the real preparation workflow.

- In [attempt 1](https://github.com/oxfa/niamodretlif/actions/runs/45052741810/job/137301281846), both receipts were accepted: worker 01 had ID `14766352338` and worker 02 had ID `14766217842`.
- In [attempt 2](https://github.com/oxfa/niamodretlif/actions/runs/45052741810/job/137301552240), worker 02 failed before upload. Its upload and receipt steps were skipped, so the observer marked it incomplete. - In [attempt 3](https://github.com/oxfa/niamodretlif/actions/runs/45052741810/job/137302411593), worker 02 uploaded ID `14765859596`, recorded it, and then failed. - The subsequent [direct-ID control](https://github.com/oxfa/niamodretlif/actions/runs/45053228225/job/137302762640), in the same repository and using `actions: read`, called GitHub's REST ZIP endpoint for those two recorded IDs. The receipt is an assertion made by the workflow using the action output; it is not an artifact-to-job relationship field supplied by the jobs API. When logs or artifacts are unavailable or validation fails, the worker is incomplete. The production implementation and other failure cases still require their own verification.

### Reusable-workflow step-log observation

The isolated [synthetic caller](https://github.com/oxfa/niamodretlif/blob/90c0201179bcb7083d0e183aeb70711fc0553593/.github/workflows/artifact-rerun-observation.yml) called a [synthetic reusable workflow](https://github.com/oxfa/niamodretlif/blob/90c0201179bcb7083d0e183aeb70711fc0553593/.github/workflows/_artifact-correlation-observation.yml) in this repository. It used two workers, `actions/upload-artifact@v7`, `actions: read`, and REST API version `2026-03-10`. Its observer printed the latest jobs API response fields and requested each successful receipt step by the step number in that response.

- In [attempt 1](https://github.com/oxfa/niamodretlif/actions/runs/45056832646/job/137313858890), the API names were `batch / Run workers (worker-01)` and `batch / Run workers (worker-02)`. Worker 01 job `137313826322` had successful receipt step 5; the step-log request returned HTTP 200 with artifact ID `14766904234`. Worker 02 job `137313826095` had successful receipt step 5; the request returned HTTP 200 with ID `14767688331`.
- In [attempt 2](https://github.com/oxfa/niamodretlif/actions/runs/45056832646/job/137314053505), only worker 02 was rerun and it failed before upload; its receipt step was skipped. The latest jobs response represented untouched worker 01 as job `137314022957`, attempt 2, with a successful receipt step 5. The step-log endpoint returned HTTP 200 and the same worker 01 receipt and artifact ID `14766904234` as attempt 1. The observer job succeeded; the workflow attempt failed as intentionally induced for worker 02.

This observation resolves the two targeted uncertainties for this synthetic same-repository reusable workflow and the tested partial rerun. It did not run the production pipeline, verify every worker count, or establish a permanent GitHub naming guarantee. Keep exact-match and missing-evidence handling, and test the resulting implementation in its actual workflow context.

The correlation design makes a step-log request, metadata request, and download request per accepted worker, plus paginated job-list requests. At the supported maximum N=20 this is at least 60 per-worker API requests, plus the paginated job-list requests. GitHub documents a `GITHUB_TOKEN` primary limit of [1,000 requests per hour per repository](https://docs.github.com/en/actions/reference/limits#commonly-hit-dependent-service-limits), with other applicable limits. This is a capacity constraint, not an observed failure at N=20. Honor rate-limit responses, do not infer missing data from them, and treat unresolved retrievals as incomplete.

## Acceptance conditions

- With the current N=18 callers, a normally completed run creates one combined worker-input artifact, one prepared-batch artifact, and 18 worker-result artifacts: 20 interstage artifacts total.
- For supported N from 1 through 20, a normally completed run has one combined worker input, one prepared-batch artifact, and N worker-result artifacts: N+2 total. The combined archive includes a directory for every worker, including empty assignments. Values outside 1 through 20 fail validation before preparation.
- The combined worker-input archive contains the exact union of worker-input members. Each runtime worker restores only the members for its matrix worker ID. Every archive contains only the members declared by its directional path layout, with the canonical paths shown above.
- The prepare job uploads the combined worker input and separate prepared-batch artifact. Do not add per-worker input artifacts or the retired `workflow-internal-worker-manifests` archive as duplicates.
- Every runtime worker downloads the combined input and restores only its own assignment directory. The aggregator selects only the prepared batch and worker bundles belonging to the applicable worker executions.
- A full or preparation rerun selects the newly prepared batch and combined input; a worker-only rerun uses the retained preparation and combined input. A missing or mismatched prepare handoff fails rather than falling back to another batch.
- A partial rerun in which any worker fails before or after upload does not enter aggregate in that failed run attempt. An artifact from an untouched or failed worker may remain available for diagnosis but is not consumed by aggregate for that attempt.
- The worker matrix uses `fail-fast: false`: an unrecoverable failure fails the full matrix and skips aggregate, while sibling workers finish and retain their logs or result artifacts when available.
- A worker that uploads a valid handoff and subsequently fails can still retain that artifact and job log for diagnosis; the overall workflow fails and aggregate remains skipped.
- The aggregator obtains each accepted worker bundle by the exact ID recorded immediately after its successful upload, checks identity and retrieval per worker, and treats missing or ambiguous receipts, logs, or artifacts as incomplete without falling back to an older bundle. If this in-aggregate correlation fails, the aggregate job fails before readiness, source-item processing, or output publication; it is not reported as a skipped job. A fatal worker execution error still fails the worker matrix and skips aggregate.
- On a successful run, preparation and participating-worker diagnostics remain available to aggregate logging through those handoff archives, and the final aggregate debug-log artifact retains its established diagnostic paths.
