## Purpose and scope

This plan records the selected prepare → worker → aggregate data contract and a dynamic replacement for `.github/artifact-uploader`. It distinguishes logical stage directions from physical artifact counts. The logical handoffs are prepare → workers (1→N), prepare → aggregate (1→1), and workers → aggregate (N→1). The selected physical package has one combined worker-input artifact named `workflow-internal-combined-worker-inputs-<batch_id>`, one separate prepare-to-aggregate artifact, and N worker-result artifacts named `workflow-internal-worker-bundle-<batch_id>-<worker_id>`: N+2 interstage artifacts total.

This plan preserves the logical stage directions and exact-ID worker-result correlation. It selects the combined-input package and requires the aggregate job to be skipped after an unrecoverable worker failure. The [artifact-handoff plan](pipeline-artifact-handoffs.md) records the same N+2 package. The current worker-count validator accepts 1 through 20; the worker matrix therefore generates at most 20 jobs, below GitHub's 256 matrix-generated jobs per workflow-run limit.

The `Current shape` column below records the pre-refactor baseline. The selected package keeps the worker matrix directly dependent on prepare; it adds no publisher job stage.

### Stage handoffs at a glance

| Handoff | Current shape | Intended responsibility |
| --- | --- | --- |
| Prepare → workers (1→N) | Prepare writes one named input artifact per worker with that worker's assigned registrable domains and runtime configuration. Each worker matrix job downloads only its exact batch-and-worker artifact. | Keep one combined artifact containing the per-worker manifests. Each runtime worker restores and processes only its own deduplicated registrable-domain assignment. | Prepare → aggregate (1→1) | One prepared-batch artifact carries output configuration, manual additions, preparation rows, source archives, and a source-line index; it does not carry worker directories. | Replace source archive replay as the source of truth with prepare-built original-item and target-association mappings, including valid items without an extracted registrable domain. | Workers → aggregate (N→1) | Each worker produces a result handoff with its unactionable registrable-domain values and domain review/terminal rows; aggregate combines the worker results. | Preserve the fan-in. Before this refactor, `.github/artifact-uploader` was already dynamic: one local-action step read the worker IDs and uploaded once per worker. It did not require 20 statically written YAML upload steps. Each runtime worker downloaded its batch-and-worker artifact, containing that worker's `runtime-config.yaml` and `assigned-roots.csv`; the roots file had deduplicated registrable-domain assignments, and the worker input had no source-item map. The hosted-action replacement uploads one combined artifact in prepare. Every worker downloads that archive and restores only its own worker directory; it processes only its own assigned registrable domains and receives no source-item mapping.

The prepare-to-aggregate artifact remains separate and carries the output configuration, worker IDs, manual additions, prepare review/terminal data, source formats, source-line index, source archives, diagnostics, and the new prepared source-item records and indexes. It does not contain worker directories. Each worker separately uploads its worker-to-aggregate result, which includes its unactionable registrable-domain values and domain review/terminal rows; aggregate correlates these result artifacts by exact artifact ID. These are three logical handoffs, not a count of physical artifacts.

## Proposed data-contract decisions

### Prepare is the authority for source parsing

Prepare parses each configured source file into per-line results and reuses those results for worker-domain planning and source-item handoff construction. In this plan, a registrable domain means a valid registrable domain extracted from a parsed target using the PSL dataset used by the prepare parser. Prepare records each item’s original content and provenance alongside its parsed target and any extracted registrable domain. Aggregate consumes these prepared records directly and reparses their item text only to validate handoff semantics; it does not replay archived source lines to reconstruct the prepare result.

Prepare builds one canonical source-item record for each item accepted by the configured source-format parser. The record has an item identity stable within the batch, source ID and label, original physical source position, input format, original text, and its target-association records. For line-based sources, derive the item identity from source identity plus the original physical line number; derive each association identity from the item identity plus its target occurrence ordinal. This keeps repeated identical lines and repeated targets distinguishable for provenance. Each association records its normalized target, PSL result, optional registrable domain, and any strict-PSL or target-syntax error. Keep the original item once; the two collections below contain references only to valid associations, so provenance is not duplicated when one item maps to several domains.

The prepare-to-aggregate handoff exposes two source-item collections:

1. `valid_source_items_by_registrable_domain`: unique PSL-derived registrable-domain keys mapped to `(item_id, association_id)` references for the target associations that yield each domain. One item may be referenced under several keys.
2. `valid_source_items_without_extractable_registrable_domain`: references to valid target associations that match the selected PSL but yield no registrable domain, plus item-level references for valid rules that have no extracted target. Keep the reason explicit, such as `public_suffix_only` or `valid_no_target`.

An item with both registrable-domain and valid no-domain associations may be referenced by both collections, with different association IDs; the no-domain collection does not mean the entire original item lacks a domain. A strict-PSL-miss target is retained as an errored association for provenance, with a matching diagnostic, and is absent from both valid collections. Preserve target occurrences and association provenance even when the same target repeats within an item; output deduplication happens later. A hosts-file line with multiple targets keeps one original-item record and a separate association for each target. Keep `manually_added_domains` as a separate prepare-to-aggregate collection; it is not a configured source item. Deduplicate rendered filtered-output lines according to the configured format while retaining every source association and its provenance in the prepared records.

Prepare continues to deduplicate the registrable-domain set used for worker assignment. It does not discard source-item occurrences or provenance merely because several items map to the same registrable domain. Any output duplicate suppression happens later under the selected output format’s rules. Syntax validation and domain extraction are separate results: an empty extraction is not proof that an item is valid, and a syntactically valid item can have no fixed domain target.

### Workers process assigned registrable domains

Each worker runtime processes only its own assigned, deduplicated registrable domains and the existing configuration metadata needed to execute them. Source-derived roots and manual additions sent to workers must be valid registrable domains under the selected PSL scope. A manual host that matches the PSL but is itself only a public suffix may remain in the existing manual review/output path; a manual host that misses strict PSL matching is invalid and must not be assigned or rendered. Workers do not load the source-item mapping or valid source items for which no registrable domain was extracted. Each worker downloads the combined input artifact and restores only its own assignment directory. The archive includes the other worker manifests, so this is an application-level routing boundary rather than per-worker authorization. The current assigned-domain manifest and per-domain assignment are the baseline for this contract.

Each worker performs lookups for its assigned registrable domains using the current prepared worker configuration. Preserve the current worker lookup classification policy for this data-flow refactor: the current delegation policy routes `ns_nxdomain_soa_absent` and `ns_empty_answer` to unactionable; retry-exhausted and unrecognized lookup outcomes route to review. A fixed routing policy classifies eligible lookup outcomes as unactionable, and the returned sidecar carries the corresponding registrable-domain values. Keep worker-result identity, schema, and duplicate-value validation. Before finalizing a worker handoff, validate that every emitted domain result belongs to that worker's loaded assigned-root set; the worker already has that set, so this check does not require copying assignment tables into prepare-to-aggregate.

The source configuration selected for a deduplicated domain is an existing policy boundary. Current prepare rejects sources that map the same registrable domain with different delegation behavior, then selects the first source in configuration order. The selected source also supplies host-resolution and IP-location settings, while the current conflict fingerprint covers delegation behavior only. Preserve that selection behavior in this data-flow refactor; changing it is a separate policy change and is not required by the new handoff model.

### Aggregate filters prepared records, then renders by format

Aggregate joins the worker `unactionable_registrable_domains` set to `valid_source_items_by_registrable_domain`. Target associations mapped to an unactionable registrable domain are excluded from source-derived filtered output; the same worker set populates the configured final unactionable-domain output. Valid source items without an extracted registrable domain do not enter worker processing. Do not equate “no registrable domain” with “no renderable target”: a PSL-matched suffix-only host can be rendered through the configured output format, while a valid AdBlock rule with no extracted host is retained only in AdBlock output and omitted from plain or hosts output. A prepare review result may coexist with filtered output.

For the user’s AdBlock examples, `/example.*/` and `/\/(ads?|advert|advertising|adserver)([\/._?-]|$)/$third-party`, a valid rule with no extracted host is retained as its original item in an AdBlock output and omitted from plain or hosts output. This records the requested behavior without treating every accepted non-domain line as valid under every source format.

The renderer applies duplicate suppression to the rendered output item, according to both input and output formats. For plain and hosts source items, filter and render target associations independently, then collapse identical rendered host lines. For a valid AdBlock network rule rendered as plain or hosts, project its destination host; omit exception rules from plain/hosts output because those formats cannot represent allow semantics. For AdBlock output from an AdBlock source, preserve original rule text and role only when its target association is valid and remains eligible. The bounded parser extracts at most one request-host target from each network rule, so no partial association rewrite is needed: omit the original rule if its target is invalid under strict PSL matching, excluded, or unactionable. Retain a valid no-target rule unchanged. For AdBlock output from plain, hosts, or dnsmasq source items, render each eligible target association as its own rule. Collapse identical rendered lines, while keeping different rules for the same registrable domain distinct. Sharing a registrable domain alone does not make distinct source items duplicates. Keep original-item provenance in the prepared records even if the renderer emits only one copy of an output line.

### Classify valid items by PSL and extraction result

Apply the user-defined validity boundary at the target association using the PSL scope selected for this refactor: a host target that has no strict PSL match is invalid and is not added to either valid-item collection. A target that matches a public suffix and yields a registrable domain belongs in `valid_source_items_by_registrable_domain`, including ordinary domains under multi-label suffixes. A target that matches the PSL but is itself only a public suffix has no registrable domain; when its source-format parser accepts it, retain that association in `valid_source_items_without_extractable_registrable_domain`. A valid AdBlock rule with no extracted host is represented there with an item-level no-target reason. Keep that case distinct from an extracted host target that fails strict PSL matching: the latter is invalid and must not become a valid no-domain association just because no registrable domain was produced.

### Pre-refactor AdBlock parser mismatch and target semantics

Before this refactor, `AdblockFormatHandler` extracted only a narrow network-rule shape, `||host^`; it returned no target for every `@@` exception and missed valid host-anchored path rules such as `||example.com/ads/*`. Its line matcher accepted many nonempty strings without whitespace, so it could not establish that an empty extraction was a valid no-target rule. `prepare_source_lines` could retain a matched line even when a parsed target failed strict PSL matching. During AdBlock output rendering, aggregate appended an original AdBlock line whenever reparsing yielded no entries. That conflated valid no-target rules with exceptions, unsupported or malformed lines, and explicit targets rejected by the PSL; a strict-PSL-miss target could therefore be re-emitted. The refactor preserves parse validity, extracted targets, and PSL outcomes as separate fields in the prepare record.

Treat source syntax, output serialization, and target extraction as separate decisions. The configured [anti-AD README](https://github.com/privacy-protection-tools/anti-AD/blob/master/README.md) identifies `anti-ad-easylist.txt` as an AdGuard Home DNS-filter list and notes that it contains regular-expression rules. The configured URL follows the moving `master` branch, so the actual source syntax inventory can change. The current [AdGuard DNS filtering syntax guide](https://adguard-dns.io/kb/general/dns-filtering-syntax/) describes its Adblock-style rules as a subset of traditional Adblock syntax and says that modifiers are engine-specific. The requested `$third-party` example is a browser-style Adblock rule, so the configured source's DNS-filter dialect cannot by itself define every valid item that may be preserved in an AdBlock output.

Use this bounded syntax profile; do not claim full compatibility with every ABP, AdGuard, or uBlock dialect:

- Recognize the known `[Adblock Plus 2.0]` list header as format metadata, not a filter item. Detect supported cosmetic rules before comment lines so `##selector` is not swallowed as a comment. Treat comments as non-filter annotations, not valid source items. Do not accept arbitrary bracketed strings as headers.
- Accept structurally valid network/domain rules with an optional leading `@@` exception marker, host-anchored patterns, path patterns, and a parsed trailing modifier list. At minimum, the profile supports `$third-party` from the supplied rule and the configured feed's observed `$dnstype` and `$denyallow` modifiers. Maintain an explicit modifier allowlist for additional constructs found in the source snapshot; an unknown modifier is not silently accepted as a valid no-target item.
- Accept slash-delimited regular-expression rules with optional `@@` and supported trailing modifiers. Parse the closing regex delimiter before interpreting a modifier clause: `$` inside the regex is part of the regex, while a later `$third-party` begins the modifier clause. Both supplied examples, `/example.*/` and `/\/(ads?|advert|advertising|adserver)([\/._?-]|$)/$third-party`, must validate and remain unchanged when the output format is AdBlock.
- Accept classic cosmetic rules using `##` and `#@#` only when the selector is nonempty. Optional domain scopes are rule context and are never worker targets. Extended cosmetic operators such as `#?#`, `#$#`, and `#%#` are outside this default profile unless a source-snapshot inventory establishes that the configured input needs them and they are explicitly added. In `auto` mode, do not treat the unsupported `#@?#` operator as a comment when the whole file is unknown or mixed; retain a source and line diagnostic for that unsupported item.

Extract a worker target only when a supported rule contains an unambiguous literal request-host. A standalone literal-domain rule or a literal host in a supported host-anchored or host/path rule maps to its PSL-derived registrable domain, for both blocking and exception rules. Wildcards in the host portion mean that no single request-host can be extracted; examples such as `||*.wildcard.example.com^` and `||adserver.*^` must not have their wildcards stripped to fabricate a host. If the rule is syntactically valid, classify it as a valid no-target item and preserve it only for AdBlock output. Regex rules, cosmetic rules, `$domain=` referring-domain scopes, and `$denyallow=` exception scopes do not produce worker targets. A concrete extracted host that misses strict PSL matching is invalid, not a valid no-target item. Preserve each original rule and its exception role in AdBlock output; omit exception rules from plain/hosts output because those formats cannot represent allow semantics.

### Validate AdBlock regular expressions as ECMAScript

The Adblock Plus guide defines slash-delimited regular-expression filters and refers readers to JavaScript regular-expression syntax. The [MDN `RegExp` constructor reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/RegExp/RegExp) states that an invalid pattern throws `SyntaxError`; MDN documents JavaScript named captures as `(?<name>pattern)` in its [named-capturing-group reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Regular_expressions/Named_capturing_group). Therefore Python `re.compile` is not the validator for this input contract.

Validate each parsed slash-delimited body with Node's ECMAScript `RegExp` constructor. In `prepare_run`, provision Node 24 with [`actions/setup-node`](https://github.com/actions/setup-node/blob/main/README.md) and disable package-manager caching because no Node packages are installed. Pass the pattern as JSON input to a fixed Node snippet; do not interpolate source text into executable code. Cache validation results for repeated pattern strings within the Python process. Treat a `SyntaxError` result as an invalid source item with a diagnostic. If Node is missing, times out, or fails unexpectedly, stop preparation with an operational error rather than accepting or rejecting the rule under a different regex grammar. Do not add an npm package or a new Python package for this validation; keep the helper with the existing AdBlock parser.

Carry recognized list metadata separately from filter items and emit it only in AdBlock output. Comments and unrecognized lines stay outside the valid filter-item collections; an empty target extraction alone must not make them valid or preserve them as rules.

Before this refactor, the parser loaded only the ICANN portion of the installed `publicsuffix2` package's `public_suffix_list.dat`, stopping at the PRIVATE section, and cached it for the process. The implementation now uses a project-bundled PSL snapshot containing both sections; its embedded header identifies version `2026-11-21_04-33-45_UTC` and commit `87a2c1b8de5886a133ff4da21b2aa6fec88d8739`. The user selected the full PSL, including ICANN and PRIVATE entries; this changes registrable-domain keys for names under private suffixes and lets hosted tenants be evaluated independently. For example, `news.example.co.uk` maps to `example.co.uk` when `co.uk` is in scope, while a target exactly equal to `co.uk` is the public suffix itself and has no registrable domain. The pipeline's strict-PSL-miss invalidity rule is an explicit policy against this bundled snapshot, not a claim that the name is universally invalid in DNS. The [PSL maintainers warn that the list changes over time](https://publicsuffix.org/learn/) and advise against stale static copies without regular updates. The snapshot revision is recorded; a repository update mechanism has not yet been established.

Use a validator for the declared syntax profile to decide whether an item is valid, and use the format parser to extract target associations. Do not use the AdBlock matcher or an empty extraction result alone as the validity test. The configured snapshot inventory is recorded above; include its observed valid constructs and modifiers in the explicit profile. Keep generic AdBlock syntax required by the supplied examples and configured AdGuard Home DNS constructs distinct in the parser contract, and do not claim full compatibility with every ABP, AdGuard, or uBlock extension. A standalone literal domain is a request-host target when the source is explicitly configured as AdBlock; a concrete target with no strict PSL match is invalid, not a valid no-target item. Keep the current whole-source format-resolution boundary for `auto`; do not add line-by-line mixed-format detection in this refactor. Do not broaden the accepted source-format set without evidence from the configured sources. Unknown or mixed `auto` inputs therefore remain outside the valid-item mapping.

### Worker-stage output names describe domain results

The worker runtime constructs one item per assigned registrable domain, with `host` and `registrable_domain` both set to that assigned value. Its `output/unactionable` text file therefore contains registrable-domain values. Its `output/review` CSV contains review-result rows for those worker domains; it is not a flat list of domains. The worker handoff model already names the returned domain field `unactionable_registrable_domains`. These are per-worker staging paths inside workflow state. Aggregate's final review and unactionable destinations are separately taken from the prepared output configuration, and aggregate review output also includes prepare-owned rows that may have no registrable domain.

The internal worker staging paths now use `unactionable-registrable-domains` and `review-results-by-registrable-domain`, matching the fact that workers process registrable domains and emit domain-result rows. `PathLayout`, the worker output manager, and worker-result archive members use these names; `tests/test_handoff_paths.py` asserts the archived paths. The handoff field `unactionable_registrable_domains`, user-configured aggregate output paths, and shared review CSV columns remain unchanged.

### Resolved source-exclusion behavior

Both current workflow callers document that `manually_excluded_from_sources` removes matching source domains before worker manifests and “emits no output rows”; non-matches are no-ops. Carry that contract through aggregate rendering: excluded target associations must not reappear in a source-derived filtered output. Keep the original item and association provenance, mark excluded associations, and omit them from worker assignments and valid-domain mappings. The current aggregate success path consumes the prepared source-item handoff rather than replaying archived source lines. It filters target associations through the prepare index before rendering; for an AdBlock source rule it preserves the original rule only when all recorded target associations remain eligible, otherwise it omits that original rule. Focused tests cover excluded AdBlock targets and hosts lines that filter each target's exclusion and PSL result independently. Duplicate suppression remains a separate output-format rule.

The current aggregate implementation has one source-item renderer: `AggregateOutputMerger.write_filtered_source_items`, which consumes the prepared handoff. The former `write_filtered_source_content` method is already absent from the current code and tests. Keep the active source archives and line index where their handoff and validation contracts still require them; do not restore an alternate archive-replay renderer.

## Code organization constraints

The current code already separates format handlers in `prepare/sources/parser.py`, prepare planning and handoff writing in `prepare/`, path contracts in `paths/layout.py`, and final rendering in `aggregate/output_merge.py`. Reuse those boundaries. The current analysis does not justify a new package or a broad OOP redesign. Add small typed item/association records within the existing prepare model and handoff modules, keep format parsing and output rendering with their current owners, and use the existing strict Pydantic handoff validation style. If later evidence requires another package, document the dependency reason and apply REP, CCP, CRP, ADP, SDP, and SAP. Any OOP/OOD must comply with SOLID, using KISS/YAGNI where a SOLID abstraction would add more complexity than this problem needs.

## Selected hosted-action implementation

### Dynamic replacement with GitHub-maintained artifact actions

`actions/upload-artifact` creates one artifact per action invocation; a shell loop cannot dynamically add more `uses:` steps to an already parsed job. The current workflow stages N worker directories in prepare and uploads them together in one action invocation. The existing worker matrix already supplies the dynamic N: each worker downloads that combined archive and restores only the directory named by its matrix ID. No publisher matrix or N statically authored upload steps are needed.

The combined artifact preserves the logical prepare → workers (1→N) assignment handoff and the direct `run_workers.needs: prepare_run` edge. Prepare → aggregate stays a separate one-artifact handoff, and workers → aggregate remains N result artifacts retrieved by exact artifact ID.

| Package design | Selection | Prepare-to-worker transfer | Worker access | Interstage artifact count | Logical worker-input transfer |
| --- | --- | --- | --- | --- |
| One combined worker-input artifact | **Selected** | Prepare uploads the combined set once; every worker matrix instance downloads it and restores its own directory. | Each worker runtime restores only its own manifest, but the full archive contains every worker's roots and runtime configuration. | `N+2` total: one combined input, one prepare-to-aggregate, N worker results. | About `(N+1)S`. |
| Combined artifact plus publisher matrix | Evaluated; not selected | N publisher instances each download the combined archive, select one worker directory, and upload one named artifact for that worker. | Runtime workers receive one per-worker artifact; publisher jobs still read the full combined set. | `2N+2` total: one combined input, N worker inputs, one prepare-to-aggregate, N worker results. | About `(N+3)S`. |

Here `S` is the total uncompressed size of all worker input files. The pre-refactor uploader sent about `2S` logically: per-worker uploads totaling `S`, followed by worker downloads totaling `S`. The combined-action package sends about `(N+1)S`: one combined upload plus N full worker downloads. The publisher-matrix option adds N full publisher downloads and per-worker uploads, for about `(N+3)S`. These are payload estimates before compression and protocol overhead; actual staged size and wire volume have not been measured.

The separate publisher jobs do not establish a hard per-worker access boundary. GitHub's `download-artifact` documentation says a same-run download can select artifacts by name (or all artifacts when no name is given), while the artifact REST API permits listing and downloading artifacts with Actions read permission. The current worker job declares `actions: read`. I infer from those permissions and interfaces that artifact names control normal workflow routing, not authorization. Since the publisher design adds jobs and transfer without proving isolation, the combined artifact is the simpler selected package. This means every worker runner downloads the other worker input directories; application restore still limits each runtime to its own assignment. Sources read directly in the Codex in-app browser: [artifact REST API](https://docs.github.com/en/rest/actions/artifacts?apiVersion=2022-11-28) and [`actions/download-artifact` README](https://github.com/actions/download-artifact/blob/main/README.md).

Preserve the hidden `.workflow_state` members when uploading (`include-hidden-files: true`) after existing allowlist staging and validation. Use `if-no-files-found: error` so an incomplete combined archive cannot appear successful. The current workflow uses `actions/upload-artifact@v7` and `actions/download-artifact@v8`, as read from their official documentation; confirm upstream versions and inputs before changing action refs. Keep batch-scoped artifact names to distinguish preparation attempts. Keep `worker_artifact_correlation.py` for worker-result retrieval: it binds job receipts to exact artifact IDs and validates result identity and contents.

Use the exact versionless receipt `ARTIFACT_RECEIPT <run_id> <batch_id> <worker_id> <artifact_id>`. Require the receipt step immediately after the successful upload step and require a positive decimal artifact ID. Do not copy the version label used by a synthetic observation workflow into the production receipt contract. ### Unrecoverable worker errors stop before aggregate

The worker must preserve an unrecoverable error's detailed cause in structured failure data and the worker log when that log is available, emit a prominent GitHub Actions `::error` annotation, and fail its job. The runtime executes the prepared pipeline in-process; `_execute_manifest_runtime` wraps exceptions with their cause text, and the CLI returns nonzero for a failure payload. The implementation keeps the primary error in the JSON payload, logs it while capture is active, treats status-write failure as secondary, and redacts manifest-configured and environment-provided IPInfo tokens from runtime failure details and provider transport warnings. Manifest validation errors omit raw input values. Initialization errors are returned as structured failure data so the workflow can reach its final error step. Failure finalization retries writing a terminal failure status when the status file is missing, and the workflow captures success- and failure-status finalization errors before its final error annotation. Failures before status initialization remain visible in their native failed workflow step; they cannot produce a worker result archive. The final worker step safely escapes arbitrary text for `::error` and exits nonzero.

Preserve the cleanup-first lifecycle: keep the processing step recoverable long enough to finalize status, stage available handoff data, and upload logs/results before a final step emits the detailed annotation and fails the worker job. Keep the worker matrix `fail-fast: false` so sibling workers can finish and retain diagnostics. Under the selected design, aggregate requires successful prepare and successful completion of the full worker matrix, with no `always()` bypass. After a fatal worker error, GitHub skips aggregate and no aggregate source-item processing or output publication runs; worker logs and uploaded result artifacts remain available where the worker reached those steps. GitHub's dependent-job and status-check documentation confirms that failed prerequisites skip dependent jobs unless an explicit status override is used. Correlation runs inside aggregate after a successful worker matrix; the correlation command now exits nonzero when any expected bundle is incomplete, so ordinary success gating prevents restore, readiness, and publication from continuing.

The internal `ready_failed` readiness state is a separate defensive path. In the current CLI, `validate-aggregate` returns nonzero for `ready_failed`, so the workflow stops before setting the readiness output or invoking the aggregate command. `AggregateBatchRunner.run()` also returns a failed result directly for that state; it does not call the separate helper that writes a failure marker or merges cache state. This path fails the aggregate job if reached, but it is not the recovery route for fatal worker errors: those fail the worker matrix and skip aggregate. Ordinary per-domain outcomes routed to review or unactionable remain distinct from unrecoverable worker execution errors.

GitHub documents matrix failure handling in [matrix strategies](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations#handling-failures), dependent-job skipping in [workflow syntax: `needs`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds), and visible error annotations in [workflow commands: setting an error message](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#setting-an-error-message). The annotation is the visible “popped up” error; failing the worker and skipping aggregate are separate workflow-control behaviors.

For comparison, the pre-refactor local-uploader topology produced `2N+1` interstage artifacts, the selected combined-input option produces `N+2`, and the unselected publisher-matrix option would produce `2N+2`. These counts include the prepare-to-aggregate artifact and N worker-result artifacts, but exclude the aggregate debug-log artifact. The [artifact-handoff plan](pipeline-artifact-handoffs.md) records the selected N+2 physical count and the three logical directions.
